# Git · PR · 배포 규칙

Git commit, push, PR 생성, merge는 개발자가 명시적으로 요청할 때만 한다.

## 작업 순서

이슈 생성 → 브랜치 생성 → 작업 → 테스트 → 커밋 → push → PR

- 이슈는 담당자를 요청자로 지정하고, 조직 프로젝트 "O(N) 개발 프로젝트"에 연결한다.
- PR 대상 브랜치는 `develop`이다. `main`은 운영 배포 브랜치다.

## 브랜치

`{커밋 타입}/#{이슈번호}-{브랜치명}` 예: `feat/#3-live-create`, `chore/#1-live-init`

커밋 타입(동사 아님): `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `ci` 등

## 커밋 메시지

한글로 쓰고 형식은 `{타입} : {메시지} (#{이슈번호})`이다. 예: `feat : 라이브 방송 생성 API 추가 (#3)`

## 커밋 전 검수

커밋을 요청받으면 아래 순서대로 진행한다.

1. 테스트를 캐시 없이 실행한다: `./gradlew test --rerun-tasks`. 통과한 경우에만 커밋한다.
2. 변경 파일을 아래 항목으로 검사한다.
   - AI 작성 흔적(`Generated by Claude` 등), 불필요한 이모지, 장식용 주석
   - 장황하거나 코드와 중복되는 주석
   - **TODO / FIXME 주석**
   - 임시 코드, 디버깅 출력문(`System.out.println` 등), 사용하지 않는 import
   - 요청한 작업과 관계없는 변경
3. **TODO / FIXME가 있으면 커밋하기 전에 위치(파일:라인)와 내용을 개발자에게 먼저 보고한다.** 개발자가 결정하기 전에는 삭제하거나 수정하지 않는다.
4. **변경 파일을 표로 먼저 보여준다.** 개발자가 확인한 뒤 커밋한다.

   | 번호 | 파일 | 상태 | 변경 내용 |
   |---|---|---|---|
   | 1 | `src/.../LiveService.java` | 추가 | 라이브 생성 유스케이스 구현 |

## PR

### 크기 제한

PR 하나는 아래 두 조건을 모두 지킨다.

| 항목 | 제한 | 확인 명령 |
|---|---|---|
| 변경 파일 수 | 20개 이하 | `git diff --name-only develop...HEAD` |
| 변경 줄 수 (추가 + 삭제) | 300줄 이하 | `git diff --shortstat develop...HEAD` |

- 작업을 시작할 때 규모를 예상해 보고, 넘을 것 같으면 **구현 전에** 개발자에게 알리고 분할 계획을 제안한다.
- 작업 중에 제한을 넘게 되면 커밋·PR 전에 먼저 알린다.

### PR stack

하나의 이슈(기능)가 크기 제한을 넘으면 PR stack으로 나눈다.

- 의미 있는 단위로 나눈다. 예: domain·port → service → adapter(web, persistence) → 테스트 보강
- 각 PR은 단독으로 빌드와 테스트가 통과해야 한다.
- 브랜치: `{타입}/#{이슈번호}-{이름}-{순번}`. 예: `feat/#3-live-create-1`, `feat/#3-live-create-2`
- 대상 브랜치: 첫 PR은 `develop`, 다음 PR부터는 바로 앞 브랜치를 대상으로 한다.
- PR 제목 끝에 순서를 붙인다. 예: `feat : 라이브 생성 도메인 추가 (#3) [1/3]`
- PR 본문 `background`에 stack 전체 목록과 현재 PR의 위치를 적는다.
- 머지는 아래에서부터 순서대로 한다. 앞 PR이 머지되면 다음 PR의 대상을 `develop`으로 바꾸고 rebase한다.

### 템플릿


```markdown
### summary
### changes
### background (or etc.)
### AI 활용 내역
- **AI 작업:**
- **개발자 작업:**
- **검증 및 리뷰:**
- **토큰 사용량:** (표)
```

- AI 활용 내역은 모두 채운다.
- 토큰 사용량은 세션 기록(`~/.claude/projects/<프로젝트>/<세션ID>.jsonl`)에서 assistant 메시지의 `usage`를 합산한다. 해당 기능을 요청한 시점부터 메시지 id 기준으로 중복 없이 더한다.

  | 구분 | 토큰 |
  |---|---|
  | 입력 | |
  | 출력 | |
  | 캐시 쓰기 | |
  | 캐시 읽기 | |
  | **합계** | |

## CI/CD

| 워크플로우 | 실행 조건 | 동작 |
|---|---|---|
| `ci.yml` | 작업 브랜치(`feat/**`, `fix/**`, `chore/**` 등) push, `develop`/`main` 대상 PR | `./gradlew clean build` |
| `deploy-dev.yml` | `develop` push | self-hosted 러너에서 빌드 후 dev 배포 |
| `deploy-prod.yml` | `main` push | bootJar 빌드 → Docker 이미지 push → EC2 배포 |

- `main`에 push되면 운영 배포가 실행된다. 배포하지 않을 커밋을 `main`에 올릴 때는 메시지에 `[skip ci]`를 붙인다.
- 서버 배포용 compose는 인프라 저장소에서 통합 관리한다.
